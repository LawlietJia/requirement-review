# 评审报告模板与产物 Schema

## 评审工作目录（每次评审）

`outputs/reviews/<需求名>-<日期>/`
- `req-items.md` — 需求条目表（S2 产物）
- `biz-items.md` — 方案要素表（S3 产物，仅有业务方案时）
- `coverage-matrix.md` — 覆盖矩阵（S7 产物，仅有业务方案时）
- `issues-ledger.md` — 问题台账（**核心产物**，schema 见下）
- `research-log.md` — 调研审计（schema 见 research-protocol.md）
- `报告.md` — 评审报告（模板见下）
- `source.docx` — 原 docx 副本（S0 条件产物，仅有 docx 输入时；**只读**——S9 回写基于它，sha256 前后须一致）
- `source-评审批注-<日期>.docx` — 评审批注副本（S9 条件产物；文件名取 source.docx 的 stem，与 writeback_docx.py 生成口径一致；Word 批注直挂原文处，author=评审人（无工具落款），原件自带他人批注保留不动）
- `docx-writeback.md` — 回写状态清单（S9 条件产物；validate_review.py section 11 校验对象，状态枚举 已批注/低置信/章节降级/未匹配）
- 迭代复审时：目录内记上轮目录相对路径；两版需求先语义 diff（按原文锚定，防编号漂移），复审只检上轮问题销号 + 改动需求 + 依赖闭包涟漪

## issues-ledger.md 固定 Schema（validate_review.py 校验对象，列名/顺序不可改）

```markdown
| F-ID | 维度 | impact_level | evidence_status | release_effect | 定位 | 原文摘录 | 问题描述与后果 | 证据来源 | 修改建议 | 关闭条件 | 澄清问题 | 状态 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| F-001 | D3 | P1 | 已确认 | 阻断 | §2.1 / L150 | "有效期为1年" | 与 §3.2"有效期为2年"矛盾，限额时效计算二义（口径冲突属"修订可关"型——按 P0/P1 评价时点分界定 P1，非 P0） | GB/T 9385 一致性 | 统一为一处口径并全文检索 | 两处口径一致且全文无第三口径 | 无 | 打开 |
```

- `F-ID`：F-001 起唯一连续
- `impact_level`：P0｜P1｜P2｜P3（若问题成立的影响）
- `evidence_status`：已确认｜较高可信｜条件成立｜待核验
- `release_effect`：阻断｜条件放行｜待澄清｜不影响放行
- `原文摘录`：文档原文字节（防幻觉锚点；**所有级别 Finding 必填**——校验器强制）
- `证据来源`：文档内证据写章节/行号；外部证据写 `URL（来源类型:法规/标准/媒体；核验日期:YYYY-MM-DD）`
- `状态`：打开｜已销号｜不适用（复审销号用）
- 表格内竖线用 `\|` 转义

## 摘录与通俗化措辞规范（V1.7.0——批注回写命中率与可读性的源头保障）

**原文摘录（回写锚点的生命线）**：
- 摘录必须从 md 原文复制字节，禁止改写、概括、换序
- 表格类问题摘整行竖线形态（如 `\| B \| 较低风险 \|`）或 cell 原文；**避免 `AAA/AA→低风险` 记法改写**——该形态只能退化为 PAIR 模糊匹配（两处命中），整行竖线形态可精确锚定
- 同一问题多处出现用 `"摘录一" + "摘录二"` 连接独立摘录，不得拼接改写成一句
- 「定位」列带章节标题词（如 `§3.1.1.1 新增-业务规则【风险等级】映射表`）——docx 标题文本不含编号，**标题词是回写消歧的主力**

**通俗化七条（台账「问题描述与后果」「修改建议」两列及报告对应节的措辞标准）**：
1. 写给需求作者本人——当其没读过评审方法论，不知道 D3/P1/术语漂移是什么
2. 先说业务后果再说机理：先"按此实现会导致国别风险拨备计提错误"，再解释技术原因
3. 术语首次出现带一句白话：如"术语漂移（同一个东西前后叫法不一致）"
4. 引用原文上下文定位：写明"第 x.x 节写…而第 y.y 节写…"，作者不必翻回原文也能定位
5. 禁空泛定性（"表述不清晰""逻辑混乱"）——必须说清谁和谁、在哪里、后果是什么
6. **禁内部过程信息**：「Run A/B」「两 run」「双跑」「上轮复现补录」「机械复核」「升格」等评审过程溯源只属于 merge-map 与「证据来源」列——绝不能出现在描述列（作者读到只会困惑；真实银行软需实测用户直接反馈看不懂）。条目间的关联用自然语句写进描述（如"其中调整分值与调整原因的关系另见 F-016"），writeback 会自动带主题展示
7. **交付级口吻（批注可当作人工评审直接交付）**：①**禁 md 行号**——「L193/L431」是转换产物的行号，作者看的是 Word 文档无从对应，定位一律用章节名/功能名/表格行内容（行号只进「定位」「证据来源」列）；②**无工具痕迹**——批注落款已移除、Word 审阅者名固定为"评审人"，描述里也不得出现"评审工具读不出""转换后不可读"等工具视角措辞（应写"该图为图片格式，内容无法随文核对"）；③口吻是评审人向作者指出问题，不是工具生成报告

以上两列文本会被 writeback_docx.py 原样搬入 docx 批注（仅做格式归一化+剥离过程注记兜底，不改写语义）——通俗化必须在台账源头完成。

## 报告.md 模板（5 必出 + 5 条件出）

```markdown
# 《<文档名>》需求评审报告（第 N 轮）

**review_status**: 已完成 ｜ 待补充        ← 先定状态；仅"已完成"出三档结论；待补充则下接"待补充后重评"与缺失清单
**评审模式**: 完整评审 ｜ 快速体检 ｜ +Gap分析    **依据方案**: <名称/版本或"无">

## 1. 总体结论
<通过 / 有条件通过（列明条件与复核判据）/ 不通过 / 待补充后重评> — 1-3 句总评
放行三问回答：①有无已确认阻断项（F-xx…）②有无妨碍判断的重要未知 ③文档是否具备决策信息
统计：P0 x / P1 x / P2 x / P3 x；阻断 x / 条件放行 x / 待澄清 x<；必须覆盖类覆盖率 x%（有方案时）>

## 2. 必须修改项（release_effect=阻断 + 条件放行的明确条件）
逐条：F-ID｜问题｜修改建议｜关闭条件（作者读后无需反问即可动手修订——这是合格线）

## 3. 必须澄清的问题（上会前必答）
按 影响×不确定性 排序，每问附"为什么问"与候选选项（无标准答案时写开放说明）

## 4. 修改判据与验证方式
修订完成后如何自查（对照 F-ID 逐条关闭条件）；复审范围建议（只复检上轮问题 + 改动涟漪抽样）

## 5. F-编号问题清单
完整台账表（或链接 issues-ledger.md）

### （仅有 docx 输入时）6. 批注副本说明
**本节在 S9c 回写完成后回填实际数据，不要预写。** 副本文件名（`source-评审批注-<日期>.docx`）｜覆盖 F-ID x/y（未覆盖列表+原因分类：摘录问题/转换噪声；**低置信列表——模糊匹配的批注位置须人工核对**）｜打开方式：Word/WPS 审阅窗格查看批注（author=评审人）；存在未匹配或低置信时本节必出（validator R5 强制）

**条件节省略规则**：条件出不满足时整节省略、**保留原编号不重排**（如无方案时第 6 节后直接第 8 节）——编号是节的稳定锚点，重排会破坏跨轮复审的引用。

### （仅有业务方案时）7. 覆盖度矩阵
BIZ↔REQ 六态矩阵 + gap 清单 + gold plating 确认清单 + 必须覆盖类覆盖率
### （可选）8. 健康度仪表盘
D1-D8 × 完整/部分/缺失 三档 + 最薄弱维度
### （条件出：有可靠依据时）9. 同业实践与优化建议
每条：**建议点｜依据分类与来源｜对本文档的适用性说明**。建议视角：流程设计（复核/审批/联动机制）、监管对标（办法鼓励或要求但本文档未覆盖的增强项）、数据治理（留痕/口径/数据质量管理惯例）、方案优化（达成同目标更简或更稳的做法）。
**依据三分类（每条建议必标其一）**：
- `法规事实`：官方原文+文号+条款+URL+核验日期（经 regulations.md 或现场核实）
- `具名同业事实`：具体机构的公开文件（办法/年报/信息披露），须给出来源名称+章节/页码锚点——**知识库 synthesis/concept 汇总页只作检索线索，不得单独支撑具名结论**
- `设计推断`：明确写"基于监管要求与工程原则的推断"——**不得表述为"同业普遍做法"**
**纪律**：建议不构成缺陷、不进台账、不影响放行结论；默认只复用评审已得证据、不为建议节单独调研（见 research-protocol.md 触发条件 8）；**无可靠依据则整节省略**；与已列缺陷重复的改进归入对应 F-ID 修改建议，不在此重复。
### 10. 亮点
零发现维度表述为"**在本次评审模式与材料范围内未发现明显问题**"（不写"满足全部检查项"——绝对化表述超出证据支撑范围）；防只批评的失衡报告
### （无 P0 时从简）11. 风险与影响
主要问题不修复进入设计开发的后果推演
```

## S0 输入完整性检查输出（报告前置声明）

报告开头（review_status 之前）附一行转换置信度声明：
`> 输入置信度：本文档由 <docx/pdf/md> 转换而来，图片文字丢失 x 处、疑似表格错位 x 处——涉图/表类检查项结论置信度受限`
转换噪声（图片缺失/表格破碎导致的"缺陷"）与源文档真实缺陷必须在报告中**区分标注**，前者标 `[转换噪声]` 不计入问题数。
