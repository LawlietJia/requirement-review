# 评审维度与检查清单（四层 × 八维）

> **使用方式**：这是检查镜头不是教程——逐维过一遍检查项，把你直觉已发现的问题归入对应维度并补全证据字段。
> **标注体系**：`[条]`=逐条需求执行｜`[档]`=整文档执行一次｜`[集]`=需求集合两两比对执行。
> **来源标注**：`[S-xx]` 对应 references/sources.md 注册表（含版本/章节/适用范围/链接/验证状态）。
> ⚠️ 标记 = 实测失手点（baseline-analysis.md / iteration score-cards），重点执行。
> **检查项本身不决定严重度**——定级走三字段（SKILL.md §定级）；**禁止任何检查项预设严重度**（发现只记录问题性质，P 级按影响评估）。

## 目录

- L 输入可信度层：D1 结构完整性
- S 单条需求层：D2 条目级质量

- B 业务方案层：D4 双向覆盖（方法见 traceability.md）｜G 外购 Gap 分析（可选开关）

## D2 条目级需求质量 [条]

| # | 检查项 | 依据 |
|---|---|---|
| D2-1 | 原子性：一条需求一个行为；多动词复合句（"生成日志并通知并刷新并清空"）必须拆分 | ISO 29148 Singular〔标准〕[S-08] |
| D2-2 | 无歧义弱词：快速/友好/灵活/支持/充分/及时/必要时/相关/美观大方/稳定高效 → 必须量化替换（"快速"→"95% 请求 ≤2 秒"） | ISO 29148〔标准〕[S-08]+Firesmith 弱词清单〔方法论〕[S-42] ⚠️基线已识别但需与 D2-4 区分处理 |
| D2-3 | EARS 化检测：每条规则能改写为 When[触发] The System Shall[响应]；改写失败点即证据——触发不唯一（"必要时"）/责任主体不明/响应不可枚举（"等""适当处理"） | EARS/Mavin〔方法论〕[S-41] |
| D2-4 | ⚠️ **无来源精确数字红旗**：凭空出现的精确阈值/数量上限（如无任何依据的"单次最多 500 条"）→ 不是采纳它为需求，而是要求出处（业务测算/监管/历史数据），无出处即按未证实陈述处理并进澄清清单 | bm629 可规划性条件〔社区〕[S-21]+证据纪律 ⚠️基线失手点 |
| D2-5 | 五要素完整：触发条件、执行角色、输入输出、规则参数（阈值/时限/频次/额度）、例外处理 | Wiegers〔方法论〕[S-40] |
| D2-6 | 验收可测：每条需求可写出 Given/When/Then 或量化判据，第三方可独立判 pass/fail | INVEST〔方法论〕[S-44] |
| D2-7 | 不预设实现：不写表结构/SQL/技术选型（行内既定约束除外） | Wiegers〔方法论〕[S-40] |
| D2-8 | 表述有据：与业务来源一致，无臆测嫁接；精确数字必有出处 | Wiegers〔方法论〕[S-40] |
| D2-9 | 单条可行：不依赖不存在的能力 | ISO 29148 Feasible〔标准〕[S-08] |
| D2-10 | 同步同源错误归并：同一错误文本在多处复制（如三处同源码值错）→ 归并为一个 Finding 计数并标注全部位置 | 评审惯例〔推断，基线已自然做到〕[S-38] |

## D7 合规与风险 [档]

## G 外购产品 Gap 分析（可选开关，仅评审对象为外购系统二开需求时启用）

每条需求标注三态：**标准功能**（产品原生）/ **配置实现**（产品可配）/ **定制开发**（改代码）；输出：定制工作量占比、产品升级兼容性风险清单（定制点在产品升级时的回归风险）。〔社区实践：外购二开评估惯例〕[S-37]
