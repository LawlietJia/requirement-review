# requirement-review

> 银行需求文档评审 Skill —— 让 LLM 评审产出**可机校、可销号、可复审**的结构化报告，而不是一段随口意见。

给 Claude Code / Codex / Cursor 等 skills-compatible agent 使用的 [Agent Skills](https://skills.sh/)。输入一份需求文档（markdown），输出：问题台账（13 列固定 schema）+ 三档放行结论 + 澄清清单 + 带证据分级的优化建议，全部经确定性校验器验证。

## 它解决什么问题

裸跑 LLM 评审需求文档的实测失手模式（本 skill 的规则全部来自对这些失手点的修复）：

| 裸跑失手 | 本 skill 的对策 |
|---|---|
| 把无来源的精确数字（"最多 500 条"）当真实需求采纳 | 无来源数字红旗 → 强制要求出处 |
| 监管条文凭记忆转述（文号/条款/罚则都可能与实际不符） | 法规清单一手核验 + 表外法规一律待核验 + 适用范围限定 |
| 缺信息时乱升 P0 撑场面 | review_status 先行：信息不足输出"待补充后重评"，不编三档结论 |
| "条件性 P1 待核验"冒充确认阻断 | 三字段定级（影响×证据×放行分轴）+ 校验器 fail-closed |
| 表述质量类缺陷（弱词/术语）被拔高成阻断 | P1→阻断三判据 + 判据适用下限 |
| "同业普遍做法"张口就来 | 建议节证据三分类（法规事实/具名同业事实须一手锚点/设计推断） |

## 核心机制

- **十步流程**（S0 受理门禁 → S9 汇总报告），每步有明确输入输出与落盘产物
- **三字段定级**：`impact_level`（P0-P3）× `evidence_status`（已确认/较高可信/条件成立/待核验）× `release_effect`（阻断/条件放行/待澄清/不影响放行）
- **阻断语义绝对化**：存在已确认阻断 → 结论必须"不通过"；可带条件关闭的缺陷标"条件放行"而非"阻断"——校验器机械强制
- **P0/P1 评价时点分界**：评审对象是尚未实施的设计，"按需求实施会违法"的口径错误属 P1（修订可关）；P0 仅限行为性违法设计与已进生产不可逆两类
- **四层八维检查**（60+ 项）：结构完整性 / 条目质量 / 一致性冲突 / 场景完整 / 非功能 / 合规 / 依赖范围 / 业务方案双向覆盖——每项标注来源与验证状态
- **三级知识调研**：项目内 → 个人知识库 → 外部（带数据安全红线：只发去标识化抽象问题，外发前用户确认）
- **确定性校验器**：`validate_review.py` 48 个测试用例——台账 schema / 阻断证据铁律 / 报告-台账一致性 / research-log 格式 / 建议节证据标签全部机检，零违规才算完成
- **同业实践与优化建议节**（条件出）：流程设计/监管对标/数据治理/方案优化四视角，每条必须带证据分级标注，无依据整节省略

## 使用

对 agent 说：

```
帮我评审这份需求说明书 <path>/需求.md，完整评审，输出报告
半小时后上会，快速过一遍这份需求有没有大问题          # 快速体检模式
这是业务方案 md，评审需求书是否实现了方案的全部设计    # 双向覆盖模式
```

产物目录：`outputs/reviews/<需求名>-<日期>/`（req-items / issues-ledger / research-log / 报告）。

## 测试与验证方法

本 skill 采用评估驱动的开发方式（方法可复用）：

- **回归集 + 盲测集两分**：调优用样本与验收用样本物理隔离（盲测集 SHA256 锁定，评审 agent 不可见答案）——调优样本的缺陷模式会渗入 skill 检查项，冻结后重跑只能证明回归不能证明泛化
- **人工裁决映射计分**：召回/严重度/放行效果按"缺陷本质"人工对齐计分，不用关键词匹配（同域近邻缺陷的文本共现会虚高命中）
- **裸跑基线对照**：skill 的每条规则可追溯到裸跑失手点
- **确定性校验器 TDD**：每个校验规则先写反例观察漏检，再实现

已知边界（如实）：LLM 评审存在 run 间方差——单次评审漏检集合有随机性，机械比对类检查（术语漂移/码值逐值/字段链）单次执行不稳定。对策已内建：重要文档双跑取并集后逐条重新裁决 + 人工复核机械比对三项。
